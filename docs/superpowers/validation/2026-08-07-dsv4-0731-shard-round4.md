# Round 4: the ranks' shard *values* have never been compared

Round 3 was clean and its elimination is sound as far as it goes: `N=2` on every
line from both ranks, all four weights moving exactly as predicted, and
`arrays_agree=True` throughout. The `scales`-versus-`weight` hypothesis is dead.

**But every probe so far compared shapes, and shapes are identical on both ranks
by construction.** Rank 0 and rank 1 both end at `wo_a.weight=(8192, 512)`. That
is what you see whether they hold *different* halves (correct) or the *same* half
(broken).

If `shard_inplace` is not applying `group.rank()` when selecting which block to
keep — taking the first segment on both ranks — then every shape is right, every
`arrays_agree` is right, and both ranks nonetheless compute the identical partial.
`_AllSumLinear` then doubles it, and the contribution of half the heads is missing
from every one of 43 layers. That produces output that is incoherent,
deterministic, and never reaches EOS.

Three probes in this investigation have now reported conclusions they could not
observe. Verify this rather than assume it.

## Step 1: fingerprint the sharded values per rank

Add after the shard, layer 0 only. `sum` over the raw packed integers is enough to
distinguish two different slices; `first8`/`last8` show *how* they differ.

```python
def _log_shard_fingerprint(label: str, weight: mx.array, rank: int, n: int) -> None:
    """Distinguish 'both ranks kept the same slice' from 'each kept its own'.

    Shapes cannot tell these apart — they are identical either way — so nothing
    in rounds 1-3 could have detected it.
    """
    flat = weight.reshape(-1)
    logger.info(
        f"shard-fingerprint N={n} r={rank} {label}: "
        f"sum={int(flat.astype(mx.uint32).sum().item())} "
        f"first8={[int(v) for v in flat[:8].tolist()]} "
        f"last8={[int(v) for v in flat[-8:].tolist()]}"
    )
```

Call it for all six sharded weights — note `up_proj`, which no previous round
probed:

```python
            if i == 0:
                r, n = self.group.rank(), self.N
                _log_shard_fingerprint("attn.wo_a", layer.attn.wo_a.weight, r, n)
                _log_shard_fingerprint("attn.wq_b", layer.attn.wq_b.weight, r, n)
                _log_shard_fingerprint("attn.attn_sink", layer.attn.attn_sink, r, n)
                _log_shard_fingerprint(
                    "switch.gate_proj", ffn.switch_mlp.gate_proj.weight, r, n
                )
                _log_shard_fingerprint(
                    "switch.up_proj", ffn.switch_mlp.up_proj.weight, r, n
                )
                _log_shard_fingerprint(
                    "switch.down_proj", ffn.switch_mlp.down_proj.weight, r, n
                )
```

`up_proj` matters on its own account. SwiGLU computes
`down(act(gate(x)) * up(x))`, so `gate` and `up` must select the **same** slice of
the intermediate dimension. If they select different halves, the elementwise
product multiplies mismatched features — garbage, deterministically, with correct
shapes everywhere. Round 3 probed `gate_proj` but not `up_proj`.

## Reading round 4

| Observation | Meaning |
|---|---|
| Every fingerprint differs between r=0 and r=1 | The ranks hold genuinely different slices. Sharding is verified for values as well as shapes, and `sanitize()` is correctly the next target — go to step 2. |
| `attn.wo_a` or `wq_b` fingerprints **identical** across ranks | **The bug.** Both ranks kept the same block; the rank index is not reaching the selection. Every layer's attention output is a doubled half. |
| `gate_proj` and `up_proj` fingerprints differ *from each other* in a way implying different halves | The SwiGLU product is multiplying mismatched features. Check that both use the same axis and rank. |
| `attn_sink` identical across ranks | Head slicing did not apply to the sink, so the sink is misaligned with the heads. |

Arithmetic to sanity-check the "same slice" reading before acting on it: on rank 0
`_shard_v4_attention_heads` keeps within-group heads 0-3, and a contiguous block
split of `wo_a`'s last axis keeps the first half, which is also within-group heads
0-3. On rank 1 both should give 4-7. So the two mechanisms *should* agree, and a
fingerprint difference between ranks is the expected outcome — I worked this
through on paper and it holds. Round 4 exists because paper is not observation.

## Step 2: compare the loaded weights against the checkpoint

`scripts/compare_loaded_vs_checkpoint.py` tests the `sanitize()` mapping directly,
with no OMLX involved. The checkpoint is the reference and it is already on disk:
same safetensors, same quantization, so a tensor `sanitize()` passes through
untouched must come back **bit-identical**. A mismatch on a pass-through tensor
names the mapping bug and says whether it was written to the wrong slot,
transposed, or reshaped.

```bash
uv run python scripts/compare_loaded_vs_checkpoint.py --verbose
```

It reads the shard index, groups layer-0 tensors by shard file, loads one shard at
a time and releases it, so peak residency is one shard plus one layer — the
earlier OOM was on evaluating all 43 layers, not on loading.

Layer 0 has 35 checkpoint tensors. Four are `attn.wq_a.*` and `attn.wkv.*`, which
`sanitize()` concatenates into the fused `wqkv_a` and which the script reports as
EXPECTED-CONCAT rather than comparing. The remaining 31 — including
`attn.wo_a.weight`/`scales`, `attn.wq_b.*`, `attn.wo_b.*`, `attn_hc.base`/`fn`/`scale`,
`ffn.gate.weight`/`tid2eid`, all six `shared_experts` and `switch_mlp` arrays, and
the four norms plus `attn_sink` — should be bit-identical.

**Run this on a single node, not the cluster.** On the cluster the weights are
sharded and would differ from the checkpoint by design.

An `ABSENT` result is not automatically benign: it means the checkpoint has a
tensor the module tree has no slot for under that name, which is exactly the
shape a mapping bug takes. Resolve each one.

## Step 3: if both come back clean

Then the weights are right and the *computation* is wrong. Compare hidden states
against OMLX layer by layer for the golden `simple_thinking_on` prompt, and find
the first layer where they diverge. One layer at a time fits in memory. The
first-token logprob comparison already established that they diverge somewhere
(OMLX top-1 `'1'`/`'H'`, EXO `'The'`); this localises where.

Candidates that a layer-0 divergence would point at, none yet examined:

* **Hyper-connections.** `attn_hc`/`ffn_hc` carry `base`, `fn` and `scale` and are
  replicated by design. My earlier notes record "replicated hyper-connections are
  correct — do not fix", but that was recorded before this defect was known, and
  `hc_mult=4` with `hc_sinkhorn_iters=20` is enough machinery to be worth
  re-deriving rather than trusting.
* **The router.** `ffn.gate.weight` plus `ffn.gate.tid2eid`, replicated. A
  `tid2eid` mapping applied inconsistently would route tokens to the wrong
  experts — deterministically, with correct shapes.
* **The Indexer and Compressor**, on `compress_ratio` layers. They take `x` and
  `qr` rather than per-head tensors, so replication looks right, but the top-k
  positions they select feed the attention mask; if those differ between EXO and
  OMLX the attention window is wrong.
